# Coffee 商家装修功能汇报讲稿（小白版）

## 0. 先说结论

我的商家装修功能本质上是一个**配置驱动的主题系统**。

商家修改颜色、图片、字体、文案和部分布局时，系统通常不会为每个商家重新生成一套小程序源码，而是修改一份主题配置 `ThemeConfig`。小程序启动后读取这份配置，再由已经发布的小程序代码把配置转换成页面样式和组件属性。

最核心的链路是：

```text
装修工作台
  -> ThemeConfig
  -> H5/真机预览
  -> 保存草稿
  -> 发布版本
  -> 门店绑定当前版本
  -> 小程序读取配置
  -> runtime.js 转换
  -> 页面显示
```

一句话概括：**代码负责“怎么显示”，配置负责“显示成什么样”。**

## 1. 先认识系统中的角色

把系统想成一家可以反复装修的店：

| 名称 | 初学者理解 | 项目中的位置 |
| --- | --- | --- |
| 装修工作台 | 商家操作颜色、图片、字体的后台页面 | `workbench.html` |
| ThemeConfig | 一份描述装修结果的 JSON | 草稿/版本中的 `config_json` |
| Controller | 接收 HTTP 请求的入口 | `DecoratorThemeController` |
| Service | 执行业务规则和校验 | `DecoratorThemeService` |
| 数据库 | 保存草稿、版本、门店绑定和资源信息 | MySQL 表 |
| Runtime | 小程序里的主题解释器 | `theme/runtime.js` |
| 页面组件 | 最终显示首页、菜单、购物车、个人中心 | `pages/*/*.vue` |

要特别区分：

- **API 是通道**，负责接收和返回数据；
- **数据库是存储**，负责把数据持久保存；
- 现在的系统是“通过 API 修改数据库”，不是“API 和数据库二选一”。

## 2. 用一个例子理解：换首页 Banner

假设商家在后台把首页 Banner 的背景色从咖啡色换成 `#8B5E3C`。

### 第一步：后台控件修改内存中的配置

工作台页面维护一个 JavaScript 对象 `state.config`。颜色控件修改的不是 Vue 文件，也不是数据库，而是对象中的某个字段，例如：

```json
{
  "schemaVersion": 1,
  "colors": {
    "primary": "#8B5E3C"
  }
}
```

这里的 `colors.primary` 就是“主色参数”。不同参数对应不同 JSON 路径，例如：

```text
颜色：colors.primary
Banner 图片：assets.homeBanner 或 slots.heroBanner.assetId
标题文字：content.homeBanner.title
字体编号：typography.bannerTitle.fontId
字体大小：typography.bannerTitle.fontSize
```

所以老师问“这个按钮背后的变量是什么”，第一步就是找到它修改了 ThemeConfig 的哪个字段。

### 第二步：H5 预览立即变化

工作台把最新配置通过 iframe 的 `postMessage` 发给 H5 预览页：

```js
{
  type: 'SKIN_CONFIG_UPDATE',
  payload: state.config
}
```

`theme/preview-bridge.js` 收到消息后调用：

```text
themeRuntime.apply(config, { persist: false })
```

这一步只是浏览器内存中的预览。此时：

- 页面看起来已经变了；
- 数据还没有写入数据库；
- 顾客端也不会变化；
- 刷新页面后，如果没有保存，修改可能消失。

### 第三步：点击保存，写入草稿

点击保存后，后台调用：

```text
PUT /coffee/decorator/themes/{themeId}/draft
```

请求体大致是：

```json
{
  "revision": 3,
  "config": {
    "schemaVersion": 1,
    "colors": { "primary": "#8B5E3C" }
  }
}
```

后端执行顺序是：

```text
DecoratorThemeController.saveDraft()
  -> DecoratorThemeService.saveDraft()
  -> ThemeConfigValidator 校验
  -> 校验图片 assetId 和字体 fontId
  -> 更新 theme_drafts.config_json
```

颜色这种普通值直接保存在 JSON 中。图片文件本身不会塞进 JSON，而是保存图片的 `assetId`。

### 第四步：revision 防止覆盖别人的修改

`revision` 可以理解为草稿的版本号。

如果窗口 A 读取的是 revision 3，窗口 B 已经保存导致版本变成 4，那么窗口 A 再拿 revision 3 保存时，后端会拒绝它，并返回 `THEME_DRAFT_CONFLICT`。

这样做是为了避免旧页面把别人刚保存的新配置覆盖掉。

## 3. 数据库每张装修表负责什么

| 表 | 作用 |
| --- | --- |
| `themes` | 装修方案的身份、名称和范围，是商家统一装修还是门店独立装修 |
| `theme_drafts` | 当前正在编辑的草稿，核心字段是 `config_json` 和 `revision` |
| `theme_versions` | 已发布的不可变版本，例如 V1、V2、V3 |
| `store_theme_bindings` | 指定每个门店当前使用哪个主题版本 |
| `theme_preview_sessions` | 保存一次真机预览的草稿快照和短期 token |
| `assets` | 图片等素材的文件地址、审核状态、尺寸和归属 |
| `theme_asset_refs` | 记录某个主题使用了哪些素材 |
| `font_resources` | 字体文件、字体名称、字重、样式和 URL |

最重要的区别是：

```text
theme_drafts = 还没有上线的修改
theme_versions = 已经发布的历史版本
store_theme_bindings = 门店当前指向哪一个版本
```

## 4. 发布以后顾客怎么拿到新配置

商家点击发布时调用：

```text
POST /coffee/decorator/themes/{themeId}/publish
```

后端会：

1. 再次校验草稿内容；
2. 计算配置哈希，防止重复发布相同内容；
3. 新增一条 `theme_versions` 记录；
4. 更新 `store_theme_bindings.published_version_id`；
5. 返回新的 `versionId`。

发布不是修改旧版本，而是创建新版本并移动门店的指针。这样可以查看历史，也可以恢复旧版本。

顾客小程序请求：

```text
GET /api/mini/skin?storeId=门店编码
```

后端先查门店绑定，再查绑定指向的版本，最后返回：

```text
config       主题 JSON
assetUrls    图片 ID 到 URL 的映射
fontResources 字体 ID 到字体信息的映射
versionId    当前版本号
```

## 5. JSON 为什么会真正影响页面

小程序代码不会自动理解任意 JSON，它有一层运行时转换逻辑。

### `normalize.js`：整理和保护配置

它负责：

- 补充缺失的默认值；
- 检查颜色格式；
- 检查字号、字重、圆角范围；
- 限制可用的组件 variant；
- 忽略或拒绝不支持的字段。

这是一层安全边界，避免商家配置任意 CSS、任意脚本或任意组件。

### `runtime.js`：把配置变成页面能用的状态

`themeRuntime.apply()` 接收到配置后，会把它保存到 Vue 响应式状态中，然后提供这些方法：

```text
themePageStyle()       页面 CSS 变量
themeSkinSlotStyle()   Banner、卡片等插槽样式
themeSkinAsset()       素材 URL
themeTypographyToken() 文字角色配置
themeComponent()       组件 variant 和显隐
```

最终链路是：

```text
ThemeConfig 字段
  -> normalize.js
  -> runtime.js
  -> Vue computed / mixin
  -> style、class、prop 或 image URL
  -> 页面显示
```

如果数据库已经有新值，但页面没有变化，问题通常在“runtime 没有读取”或“页面没有消费这个字段”，不一定是数据库问题。

## 6. 图片和字体是怎样工作的

### 图片链路

```text
上传图片
  -> assets 表生成 assetId
  -> 审核通过
  -> ThemeConfig 只保存 assetId
  -> 发布时校验素材仍然有效
  -> API 返回 assetUrls
  -> runtime.assetUrl(assetId)
  -> <image> 或 background-image
```

这样设计的好处是：图片文件和业务配置分开，图片可以复用、审核、停用和替换。

### 字体链路

```text
字体文件
  -> font_resources 表
  -> typography.bannerTitle.fontId
  -> API 返回 fontResources
  -> font-loader.js 加载字体
  -> CSS font-family / font-weight / font-style
  -> 页面文字使用字体
```

字体不是一张图片。字体配置可以包含字号、字重、行高、字距和字体资源编号。H5 使用 `FontFace`，小程序环境使用 `uni.loadFontFace()`。

## 7. 预览、保存、发布要分清

### H5 即时预览

```text
前端内存配置 -> postMessage -> H5 页面
```

速度快，但不代表已经保存或上线。

### 保存草稿

```text
PUT /draft -> theme_drafts
```

保存后可以继续编辑，但顾客仍然看不到。

### 真机预览

```text
保存草稿
  -> 创建 preview session
  -> 得到 previewToken
  -> 小程序用 token 读取草稿快照
```

真机预览只读草稿，不改变线上版本；token 过期或撤销后不能再访问。

### 正式发布

```text
草稿
  -> theme_versions 新版本
  -> store_theme_bindings 切换
  -> 顾客 API 返回新版本
```

## 8. 老师问“要不要重新打包”时怎么回答

要分两种变化：

| 变化 | 是否需要重新编译小程序 |
| --- | --- |
| 改颜色、图片、字体、文案、支持范围内的布局 | 通常不需要，只更新 ThemeConfig 和资源 |
| 新增页面、修改业务逻辑、增加组件代码、修改 API | 需要开发者重新构建并走微信小程序发布流程 |

项目里的 `getUpdateManager()` 处理的是开发者发布了新的小程序代码包之后的版本更新，不是商家装修配置的发布。

所以当前项目的“增量更新”准确说法是：

```text
下载新的配置和资源，切换 versionId
```

不是：

```text
重新生成每个商家的 WXML、WXSS、JS 并上传代码包
```

## 9. 出问题时的排查顺序

### 情况一：控件变了，H5 没变

依次查：

```text
工作台事件有没有修改 state.config
  -> postMessage 有没有发送
  -> preview-bridge.js 有没有接收
  -> runtime.apply() 有没有执行
  -> normalize.js 有没有丢弃字段
  -> 页面有没有消费这个字段
```

### 情况二：H5 变了，刷新后没了

查保存链路：

```text
PUT /draft
  -> Controller
  -> Service
  -> Validator
  -> theme_drafts.config_json
```

### 情况三：草稿保存了，顾客没变

查发布链路：

```text
是否点击发布
  -> theme_versions 是否新增
  -> store_theme_bindings 是否指向新版本
  -> /api/mini/skin 返回的 versionId 是否变化
```

### 情况四：API 是新值，页面还是旧样式

查：

```text
normalize.js
  -> runtime.js
  -> 页面 computed / mixin
  -> 页面模板中的 style、class 或组件 prop
```

## 10. 可以直接向老师汇报的版本

> 我的商家装修功能采用配置驱动的运行时主题模式，而不是给每个商家重新生成一套小程序源码。商家在装修工作台修改颜色、图片、字体和布局时，前端先修改 ThemeConfig，并通过 postMessage 更新 H5 预览。点击保存后，前端调用草稿 API，后端经过权限、Schema、素材和字体校验，以 revision 乐观锁保存到 `theme_drafts.config_json`。点击发布后，系统把草稿固化成不可变的 `theme_versions`，再通过 `store_theme_bindings` 指定门店当前使用的版本。顾客小程序通过 `/api/mini/skin` 读取当前门店版本，`themeRuntime` 和 `normalize` 将配置转换为 CSS 变量、组件属性、图片地址和字体样式，最后由页面渲染出来。因此，商家修改主题通常只需要更新配置和资源，不需要重新编译微信代码包；只有页面结构、业务逻辑或组件代码变化时，才需要开发者重新打包发布。>

## 11. 老师可能继续追问

### 问：到底是调用 API 还是直接改数据库？

答：后台通过 API 调用后端 Controller，Controller 进入 Service，Service 校验后由 Mapper 修改数据库。前端不应该直接连接数据库。

### 问：为什么不直接把 CSS 存数据库？

答：直接存任意 CSS 难以校验、安全性差、跨端表现不稳定。现在保存的是受 Schema 约束的结构化配置，由运行时统一转换成样式。

### 问：为什么要有草稿和发布版本？

答：草稿用于编辑和预览，发布版本用于线上读取。分开可以避免商家编辑到一半就影响顾客，也可以保留历史并支持恢复。

### 问：为什么图片保存 assetId，不保存图片 URL？

答：素材需要审核、归属校验、停用和 URL 管理。配置保存稳定的 assetId，API 再根据当前资源状态返回 URL。

### 问：为什么要有门店绑定表？

答：同一个商家可能有多个门店，有的跟随统一主题，有的使用独立主题。绑定表明确记录每个门店当前使用哪个版本。

### 问：如果 AI 生成了装修代码，你怎么看？

答：AI 可以帮助生成工作台、运行时或校验代码，但开发者必须理解参数路径、数据流、数据库表和页面消费关系，才能维护和排错。AI 生成不是理解的替代品。

## 12. 你应该按什么顺序学习

不要一开始试图看完整个项目，按这个顺序：

```text
1. 先看首页 Banner 颜色
2. 再看 Banner 图片 assetId
3. 再看保存草稿和 revision
4. 再看发布、版本和门店绑定
5. 再看小程序 GET /api/mini/skin
6. 再看 runtime.js 如何把配置变成样式
7. 最后看字体、布局、艺术字和 AI 背景
```

每学一个功能，都回答这 8 个问题：

```text
它在工作台哪个控件？
它修改 JSON 哪个字段？
它怎么即时预览？
它保存调用哪个 API？
它最终存哪张表？
发布后哪个版本和绑定发生变化？
小程序从哪个 API 读？
页面最终在哪里消费它？
```

能完整回答这 8 个问题，就已经不是“只会看界面”，而是在理解这个功能的实现逻辑。
