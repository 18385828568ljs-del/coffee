# Coffee 商家装修功能代码导读

这份文档不是通用装修系统教程，而是按照当前项目代码解释：商家在后台改一个装修参数以后，数据经过哪些对象、接口、数据库表和小程序代码，最后如何出现在页面上。

## 先记住一句话

当前项目采用的是：

```text
编辑器修改 ThemeConfig
  -> H5 本地即时预览
  -> PUT 保存到 theme_drafts.config_json
  -> POST 发布生成 theme_versions
  -> store_theme_bindings 切换门店当前版本
  -> 小程序 GET /api/mini/skin 读取 JSON
  -> runtime.js 规范化并转换为 CSS、组件属性和图片地址
```

它不是“商家改一次颜色，就重新生成一套 WXML/WXSS/JS”。页面代码已经随小程序包发布，商家变化的是数据库中的配置和素材引用。

## 一、先区分六个概念

| 概念 | 作用 | 是否让顾客立即看到 |
| --- | --- | --- |
| `config` | 前端当前正在编辑的完整主题 JSON | 只影响编辑器预览 |
| `theme_drafts` | 商家保存但尚未上线的草稿 | 不影响顾客 |
| `theme_preview_sessions` | 绑定某次草稿 revision 的短期真机预览快照 | 只影响拿到 token 的预览者 |
| `theme_versions` | 发布后不可变的主题版本 | 可被线上读取 |
| `store_theme_bindings` | 某门店当前指向哪个主题版本 | 决定门店线上使用哪一版 |
| `assets` / `font_resources` | 图片、字体等资源的元数据和 URL | 被配置引用后才影响页面 |

其中 `themes` 是装修方案的身份和作用域，不是配置正文；正文在草稿或版本的 `config_json` 中。

## 二、商家改一个颜色时，完整链路是什么

假设商家把首页主题主色改成 `#8B5E3C`。

### 1. 编辑器先改 JavaScript 内存对象

工作台维护 `state.config`。颜色控件修改的是这个对象中的路径，例如：

```json
{
  "schemaVersion": 1,
  "colors": {
    "primary": "#8B5E3C"
  }
}
```

项目同时兼容旧的 `schemaVersion: "1.0.0"` 配置和当前皮肤配置 `schemaVersion: 1`。工作台加载草稿后会把 `configJson` 解析成 `state.config`，因此不要把页面 CSS 直接当作装修数据。

### 2. H5 预览不需要请求后端

工作台把最新的 `state.config` 通过 iframe 的 `postMessage` 发给 uni-app H5 预览页：

```js
{
  type: 'SKIN_CONFIG_UPDATE',
  payload: state.config,
  assetUrls: ..., 
  fontResources: ...
}
```

`theme/preview-bridge.js` 收到消息后调用 `themeRuntime.apply(..., { persist: false })`。所以拖动颜色控件时，最先发生的是浏览器内存中的渲染变化，不是数据库更新。

### 3. 保存按钮才调用后端草稿接口

接口是：

```text
PUT /coffee/decorator/themes/{themeId}/draft
Body: { revision, config }
```

`DecoratorThemeController.saveDraft()` 将 `config` 序列化后交给 `DecoratorThemeService.saveDraft()`。服务层会依次做：

1. 检查当前用户是否有 `THEME_EDIT` 权限以及是否属于该商家/门店；
2. 用 `ThemeConfigValidator` 校验 schema、颜色、字段和组件枚举；
3. 校验嵌套的图片 `assetId` 和字体 `fontId` 是否属于当前商家、处于可用状态；
4. 序列化成规范 JSON；
5. 按 `revision` 做乐观锁更新；
6. 将图片引用同步到 `theme_asset_refs`。

因此，颜色这种纯值主要存进 `theme_drafts.config_json`；图片本体不存进 JSON，而是 JSON 引用 `assetId`，图片信息在 `assets`，引用快照在 `theme_asset_refs`。

### 4. revision 防止两个窗口互相覆盖

保存条件相当于：

```sql
UPDATE theme_drafts
SET config_json = ?, revision = revision + 1
WHERE merchant_id = ? AND theme_id = ? AND revision = ?;
```

更新行数不是 1 时，后端返回 `THEME_DRAFT_CONFLICT`。这意味着保存请求不能只传 JSON，还必须带上你读取到的 revision。

## 三、参数怎样真正作用到页面代码

小程序不是把 JSON 当作 HTML 显示，而是有一层运行时适配。

### 颜色、圆角、阴影

`theme/runtime.js` 的 `apply()` 收到配置后调用 `normalizeSkinConfigV1()` 或 `normalizeThemeConfig()`，补默认值并拒绝非法值。随后页面通过 `themePageStyle`、`themeSkinSlotStyle()` 等方法把配置转成内联样式或 CSS 变量。

页面一般通过 `themeMixin` 取得这些能力，例如：

```text
themePageStyle       -> 页面级 CSS 变量
themeSkinSlotStyle   -> heroBanner、orderCard 等插槽样式
themeSkinAsset       -> 素材 URL
themeTypographyToken -> 文字角色配置
themeComponent       -> 组件 variant 和显隐配置
```

所以“参数作用于代码”的准确说法是：

```text
JSON 字段
  -> normalize 默认值/白名单
  -> runtime 辅助函数
  -> Vue 页面 computed 或组件 prop
  -> style/class/图片 URL
  -> 页面渲染
```

如果一个控件改了 JSON，但页面没有变化，优先检查这条链中是否缺少消费方，而不是先怀疑数据库。

### 组件 variant

例如 `components.productCard.variant` 可以是 `vertical` 或 `horizontal`。`normalize.js` 会调用 `isAllowedVariant()`，页面组件再根据 `theme-variant` 或计算属性选择对应布局。这里改变的是同一份页面代码的分支，不是生成新页面文件。

### 文案和布局

`content.homeBanner.title`、`layout.homeBanner.contentPreset` 等字段经过规范化后，由首页的 computed 或模板读取。它们仍然是配置数据，不是后端修改 Vue 文件。

## 四、图片参数和字体参数的区别

### 图片

图片上传后先成为 `assets` 记录，只有审核通过且状态为 `ACTIVE` 才能被主题引用。配置保存时写入 `assetId`，服务端生成 `assetUrls` 映射；小程序拿到映射后用 `assetUrl(assetId)` 解析成真正 URL。

图片完整链路：

```text
上传文件
  -> assets.id
  -> config.assets / config.slots / config.decorations 中保存 assetId
  -> theme_asset_refs 保存用途
  -> 发布时再次校验
  -> API 返回 assetUrls
  -> runtime.assetUrl(assetId)
  -> image 或 background-image
```

### 字体

字体不是把文字转成图片。`typography.<role>` 中保存颜色、字号、字重、行高、字距，以及可选的 `fontId`。

例如：

```json
{
  "typography": {
    "bannerTitle": {
      "fontId": 12,
      "fontSize": 26,
      "fontWeight": 800,
      "lineHeight": 1.2
    }
  }
}
```

后端 `DecoratorFontService` 从 `font_resources` 查询可用字体，返回 `familyName`、`url`、`weight`、`style`。前端 `font-loader.js` 使用 H5 的 `FontFace` 或小程序的 `uni.loadFontFace()` 加载字体；`typography-registry.js` 再生成诸如 `--skin-banner-title-family` 的 CSS 变量。

字体链路是：

```text
fontId
  -> font_resources
  -> API fontResources
  -> loadFontResources()
  -> CSS font-family / font-weight / font-style
  -> 带 data-text-role 的文字节点
```

## 五、预览、保存、发布分别做什么

### A. H5 即时预览

用途是编辑体验。它直接消费内存中的配置，通过 `postMessage` 更新 iframe，`persist: false`，不会写草稿，也不会影响顾客。

### B. 保存草稿

用途是把当前编辑结果可靠保存。它写 `theme_drafts.config_json`，revision 加 1，但不改变 `theme_versions` 和门店绑定。

### C. 真机预览

接口：

```text
POST /coffee/decorator/themes/{themeId}/preview-sessions
Body: { storeId, revision }
```

后端把当前草稿快照复制到 `theme_preview_sessions.config_json`，只保存 token 的 SHA-256 哈希，返回短期 `previewToken`。小程序用：

```text
GET /api/mini/skin?storeId={storeCode}&previewToken={token}
```

带 token 时后端优先返回预览快照，不读取线上版本。预览接口是只读的，过期或撤销后返回 `THEME_PREVIEW_EXPIRED`。

### D. 发布

接口：

```text
POST /coffee/decorator/themes/{themeId}/publish
Body: { revision, idempotencyKey, publishNote }
```

`DecoratorThemeService.publish()` 会：

1. 锁住并确认草稿 revision；
2. 再次校验配置、图片和字体；
3. 计算规范 JSON 的 SHA-256 `configHash`；
4. 如果与最新版本相同，拒绝为 `THEME_NOT_CHANGED`；
5. 插入一条不可变 `theme_versions`；
6. 商家统一主题：更新所有跟随统一主题的门店绑定；
7. 门店独立主题：只更新目标门店绑定。

发布不是修改旧版本，而是创建新版本并移动绑定指针。这就是可审计、可恢复的发布模型。

## 六、小程序线上读取和“增量更新”

顾客端请求：

```text
GET /api/mini/skin?storeId=店铺编码
```

后端通过 `store_theme_bindings.published_version_id` 找到 `theme_versions.config_json`，再返回 `config`、`assetUrls` 和 `fontResources`。

小程序 `themeRuntime.loadPublished()` 会：

1. 先读取本地缓存，避免白屏；
2. 请求当前门店的版本号；
3. 版本没有变化时复用配置缓存；
4. 版本变化时重新下载配置和资源地址；
5. 调用 `apply()` 规范化并更新 Vue 响应式状态；
6. 将新版本写入本地缓存。

所以当前实现的“增量”是：

```text
只下载新的 ThemeConfig/资源，并切换 versionId
```

不是：

```text
商家每次发布都重新编译、上传、审核整个微信小程序代码包
```

微信 `getUpdateManager()` 处理的是开发者发布新代码包后的版本更新，例如页面结构或业务逻辑改变；它不负责主题 JSON 的商家发布。两条更新链必须分开理解：

| 更新类型 | 触发者 | 典型内容 | 是否需要重新编译小程序 |
| --- | --- | --- | --- |
| 主题数据发布 | 商家 | 颜色、图片、字体、文案、白名单布局 | 否 |
| 业务代码发布 | 开发者 | 新页面、接口逻辑、组件代码 | 是，需要微信审核/发布流程 |

## 七、商家统一装修和门店独立装修

项目不是简单地把 `merchantId` 写进配置，而是用绑定关系表达作用域：

- `MERCHANT` 主题发布后，`bindFollowingStores()` 更新仍处于 `FOLLOW_MERCHANT` 的门店；
- 门店切换到独立主题后，发布只更新该门店的 `INDEPENDENT` 绑定；
- `follow-master` 可以让门店重新指向统一主题当前版本；
- 独立主题创建时复制一份完整配置快照，不在运行时做复杂字段继承。

这也是为什么查询线上主题时必须先查门店绑定，再查 `published_version_id`，不能只查“商家当前主题”。

## 八、你现在应该怎样自己追一个控件

以后拿到“换按钮颜色”“换 Banner 图片”这类任务，按下面六步排查：

1. 在工作台找控件事件，确认它修改 `state.config` 的哪个 JSON 路径。
2. 在 `workbench.html` 确认即时预览消息中是否包含该字段。
3. 在 `normalize.js` 确认该字段是否被白名单接收、是否有默认值和范围校验。
4. 在小程序页面和 `runtime.js` 搜索该字段的消费函数，确认它最终变成什么 style/class/prop。
5. 点击保存，检查 `PUT /draft`、revision 和数据库 `theme_drafts.config_json` 是否变化。
6. 点击发布，检查 `theme_versions`、`store_theme_bindings` 和线上 `GET /api/mini/skin` 返回的 versionId 是否变化。

只要第 1 至第 4 步通了，页面即时预览就应该通；第 5 步通了，草稿持久化就通；第 6 步通了，线上发布闭环才通。

## 九、当前实现需要你特别记住的边界

### 已有能力

- 主题/草稿/版本/门店绑定的基本闭环；
- revision 乐观锁；
- 配置 schema 和默认值规范化；
- 图片素材引用校验；
- 字体资源校验和加载；
- H5 即时预览；
- 短期真机预览 token；
- 发布幂等键和不可变版本。

### 不能直接从现有代码得出的结论

- 不能说系统已经“生成了每个商家的微信小程序源码”；当前代码没有把 ThemeConfig 反向生成 WXML/WXSS/JS。
- 不能说已经实现了微信代码包的二进制增量发布；当前实现的是运行时配置增量。
- 不能把 `theme_drafts` 当线上数据；顾客端只读发布版本绑定。
- 不能把图片 URL 直接塞进任意配置而跳过 `assets` 审核和引用校验。
- 不能把字体当普通图片；字体是 `font_resources` + `fontId` + 运行时字体加载。

另外，工作台文案写着“预览有效期 15 分钟”，而 `DecoratorPreviewService` 当前常量是 30 分钟。正式验收前应统一这个产品口径，并补缓存失效、审计日志和真实微信开发者工具联调。

## 十、面试或汇报时的标准讲法

你可以这样回答：

> 我们的商家装修不是修改小程序源码，而是配置驱动的运行时主题系统。编辑器先在前端维护 ThemeConfig，通过 postMessage 做 H5 即时预览；保存时调用草稿 API，经 schema、租户、素材和字体校验后，以 revision 乐观锁写入 theme_drafts。发布时把草稿固化成不可变的 theme_versions，再通过 store_theme_bindings 指定门店当前版本。小程序启动或切店时调用 /api/mini/skin，按 versionId 缓存并把配置规范化成 CSS 变量、组件 variant、布局和素材/字体资源。因此商家改颜色、图片、字体通常不需要重新编译微信代码包，这是一种配置和资源的增量更新；只有页面逻辑或组件代码变化时，才需要开发者重新构建并走微信版本发布流程。>

这段话能同时回答“参数存哪儿”“API 还是数据库”“如何作用于代码”“如何发布”“增量更新是什么”，而且与当前仓库实现一致。
