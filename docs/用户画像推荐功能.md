# 用户画像推荐功能

## 功能定位

基于用户行为数据的商品排序引擎。从最近 180 天的浏览、加购、购买中提取偏好，自动调整商城和点单商品顺序。

**特点**:
- 内部推荐，不向用户展示画像
- 商城(MALL)和点单(SCAN)分场景独立计算
- 价格优先策略（价格距离 > 标签匹配度）
- 推荐失败返回原顺序，不阻塞主流程

## 工作流程

```
用户行为
  ├─ 浏览详情 → PRODUCT_VIEW (权重1)
  ├─ 首次加购 → CART_ADD (权重4)
  └─ 完成订单 → PURCHASE (权重8)
       ↓
行为证据表 (t_user_behavior_event)
订单证据 (t_order + t_scan_order)
       ↓
定时任务
  ├─ 每10分钟: 增量刷新变化用户
  └─ 每天03:00: 全量校准 + 清理过期数据
       ↓
画像计算
  ├─ 读取近180天证据
  ├─ 应用行为权重 (8/4/1)
  ├─ 应用时间衰减 (1.0/0.6/0.3)
  ├─ 提取多维度标签
  └─ 生成价格区间标签 (10元一档)
       ↓
用户画像表 (t_user_profile)
  ├─ EMPTY: 无证据
  ├─ LEARNING: 1-2条行为且无购买
  └─ READY: ≥1条购买 或 ≥3条行为
       ↓
商品列表请求
       ↓
推荐排序
  ├─ 计算价格距离
  ├─ 累加标签匹配分
  └─ 排序: 价格距离升序 → 标签分降序
       ↓
返回排序后商品列表
```

## 行为证据采集

### 证据类型与权重

| 证据 | 权重 | 采集时机 | 去重规则 |
|------|------|---------|---------|
| PRODUCT_VIEW | 1 | 打开商品详情 | 同用户+场景+商品每天一次 |
| CART_ADD | 4 | 购物车行首次创建 | 按购物车行ID去重 |
| PURCHASE | 8 | 有效订单明细 | 每条明细一条证据 |

### 有效购买定义

**商城订单**: 状态为待发货/已发货/已完成，且未退款，排除赠品  
**点单订单**: 状态为制作中/待取餐/已完成，且未退款

### 去重机制

**浏览**: `UNIQUE KEY(dedup_key)` = `PRODUCT_VIEW:MALL:userId:productId:20260823`  
**加购**: `UNIQUE KEY(dedup_key)` = `CART_ADD:SCAN:cartId`

数据库唯一索引防重复，代码捕获 `DuplicateKeyException` 返回 false。

### 场景隔离

| 场景 | 标识 | 典型商品 |
|------|------|---------|
| 商城 | MALL | 咖啡豆、器具、滤纸 |
| 点单 | SCAN | 饮品、小食、现磨咖啡 |

避免"买咖啡豆"和"现场点饮品"的偏好相互污染。

## 画像计算算法

### 时间衰减

| 证据年龄 | 衰减系数 |
|---------|---------|
| 0-30天 | 1.0 |
| 31-90天 | 0.6 |
| 91-180天 | 0.3 |
| >180天 | 0.0 (不参与) |

**证据得分** = 行为权重 × 时间衰减系数

示例:
- 20天前购买: `8 × 1.0 = 8.0`
- 60天前加购: `4 × 0.6 = 2.4`
- 100天前浏览: `1 × 0.3 = 0.3`

### 标签提取

**商城标签** (MALL):
- product, category, origin, processing, roast, flavor, price

**点单标签** (SCAN):
- product, category, type, cup, temperature, bean, strength, sugar, price

**规格处理**:
- 浏览: 只提取商品、分类、类型
- 加购/购买: 包含用户实际选择的规格

### 价格标签生成

1. 按 10 元分桶: `19.00→10-19.99`, `25.00→20-29.99`
2. 累加落在同一桶的证据分数
3. 选择总分最高的桶作为偏好区间
4. 分数相同时选择更低的桶

**存储格式**:
```json
{
  "key": "price:60.00-69.99",
  "dimension": "price",
  "name": "60.00-69.99",
  "score": 8.00,
  "min": 60.00,
  "max": 69.99
}
```

### 画像状态

| 状态 | 条件 | 是否推荐 |
|------|------|---------|
| EMPTY | 无证据 | 否 |
| LEARNING | 1-2条行为且无购买 | 否 |
| READY | ≥1条购买 或 ≥3条行为 | 是 |

### 画像数据结构

```json
{
  "MALL": {
    "tags": [
      {
        "key": "category:11",
        "dimension": "category",
        "name": "咖啡豆",
        "score": 14.00,
        "evidenceCount": 4,
        "lastEvidenceTime": "2026-08-20 10:00:00"
      },
      {
        "key": "price:60.00-69.99",
        "dimension": "price",
        "name": "60.00-69.99",
        "score": 8.00,
        "min": 60.00,
        "max": 69.99
      }
    ]
  },
  "SCAN": { "tags": [...] }
}
```

## 推荐排序算法

### 商品得分计算

**价格距离**:
```
IF 商品价格在 [min, max] 内:
    价格距离 = 0
ELSE IF 商品价格 < min:
    价格距离 = min - 商品价格
ELSE IF 商品价格 > max:
    价格距离 = 商品价格 - max
```

**标签匹配分**: 商品标签命中画像标签的分数总和

### 排序规则

```
第一优先级: 价格距离升序 (越接近偏好区间越靠前)
第二优先级: 标签匹配分降序 (命中标签越多越靠前)
```

**示例**:

假设用户偏好价格区间 `20-29.99`

| 商品 | 价格 | 价格距离 | 标签分 | 排序 |
|------|------|---------|--------|------|
| B | 29.00 | 0 | 12 | 1 |
| A | 25.00 | 0 | 3 | 2 |
| C | 32.00 | 2.01 | 30 | 3 |
| D | 40.00 | 10.01 | 5 | 4 |

**说明**: C 虽然标签分最高，但价格超出区间，排在 A/B 后面。

### 失败降级

以下情况返回原商品顺序:
- 用户未登录
- 画像状态不是 READY
- 画像 JSON 解析失败
- 推荐计算异常
- 无价格标签且无标签匹配

### 调用流程

```
小程序请求 (携带 Token)
    ↓
Controller 解析 userId
    ↓
Service 查询上架商品
    ↓
推荐服务排序
    ├─ 读取 READY 画像

    └─ 排序返回
    ↓
营销引擎计算价格
    ↓
分页返回小程序
```

## 定时任务调度

### 任务配置

| 任务 | Cron | 说明 |
|------|------|------|
| 增量刷新 | `0 0/10 * * * ?` | 每10分钟处理变化用户 |
| 全量校准 | `0 0 3 * * ?` | 每天03:00重算全部 + 清理过期数据 |

### 增量刷新逻辑

查询以下用户:
1. 新用户（在 t_wxuser 但不在 t_user_profile）
2. 有新行为的用户（行为时间 ≥ 画像时间 - 10分钟）
3. 有新订单的用户（订单时间 ≥ 画像时间 - 10分钟）

**10分钟重叠窗口**: 避免任务边界处漏算

### 全量校准逻辑

1. 清理超过 180 天的行为记录
2. 查询所有微信用户
3. 逐个重新计算画像

**并发控制**: `synchronized` 方法防止同一实例内并发

## 数据表

### t_user_behavior_event (行为证据)

关键字段: user_id, event_type, scene, product_id, spec_json, dedup_key, event_time

唯一索引: `dedup_key` 防止重复

### t_user_profile (用户画像)

| 字段 | 说明 |
|------|------|
| user_id | 主键 |
| profile_status | EMPTY/LEARNING/READY |
| profile_data | JSON (MALL + SCAN 标签) |
| calculate_time | 最近计算时间 |

### 购买证据来源

- 商城: `t_order` + `t_order_item` + `t_product`
- 点单: `t_scan_order` + `t_scan_order_item` + `t_scan_product`

## 性能与优化

### 性能指标

- 单用户画像计算: < 100ms
- 推荐排序: < 10ms
- 增量刷新 1000 用户: 1-2 分钟
- 全量校准 10000 用户: 15-30 分钟

### 优化建议

**Redis 缓存**:
```java
// 画像缓存 TTL=10分钟
String key = "user_profile:" + userId;
profile = redis.get(key);
if (profile == null) {
    profile = db.query(userId);
    redis.set(key, profile, 600);
}
```

**并行计算**:
```java
ExecutorService executor = Executors.newFixedThreadPool(10);
for (Long userId : userIds) {
    executor.submit(() -> calculateProfile(userId));
}
```

**索引优化**:
```sql
-- 复合索引加速查询
ALTER TABLE t_user_behavior_event 
ADD INDEX idx_user_scene_time (user_id, scene, event_time);
```

### 多实例部署改造

1. 画像缓存使用 Redis
2. Quartz 启用集群模式
3. 增加分布式锁防止全量任务并发

**Quartz 集群配置**:
```yaml
spring:
  quartz:
    job-store-type: jdbc
    properties:
      org.quartz.jobStore.isClustered: true
```

## 常见问题

**Q: 推荐没有生效？**

排查步骤:
1. 用户是否登录（Token 有效性）
2. 画像状态是否为 READY
3. 定时任务是否正常运行
4. 画像 JSON 是否包含标签

**Q: 画像更新延迟多久？**

最多 10 分钟（增量任务周期）

**Q: 多实例部署注意事项？**

1. Quartz 启用集群模式
2. 画像缓存使用 Redis
3. 增加分布式锁

**Q: 如何调整权重？**

当前硬编码在 `UserProfileService.java`，建议改为配置化。

## 总结

**优点**:
- 算法合理（价格优先、时间衰减、场景隔离）
- 工程扎实（去重、降级、容错）
- 性能可接受（单次 < 10ms）

**局限**:
- 硬编码配置多
- 缺少缓存层
- 冷启动无推荐

**适用场景**: 单店、日活 < 1000、单机部署
